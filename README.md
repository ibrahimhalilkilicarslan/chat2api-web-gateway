# Chat2API DeepSeek Web Gateway

A security-hardened, web-only OpenAI-compatible gateway backed by isolated
DeepSeek web sessions. It includes a responsive operations console for provider
health, client keys, quotas, request metadata, and security audit events.

> [!IMPORTANT]
> This project uses an undocumented DeepSeek web protocol. It is not an official
> DeepSeek API client. Provider changes, account controls, or terms may interrupt
> access. Use dedicated accounts and evaluate provider terms before production use.

## What is included

- OpenAI-compatible `GET /v1/models`
- OpenAI-compatible `POST /v1/chat/completions`
- JSON and SSE streaming responses
- Encrypted DeepSeek credential storage
- Hashed, scoped, rate-limited client API keys
- Account health checks, circuit breakers, quotas, and concurrency limits
- Metadata-only request activity and admin audit logs
- Responsive admin console at `/admin/`
- Non-root, read-only, capability-free Docker runtime

Electron, desktop sessions, browser automation, official API fallback, arbitrary
providers, remote media, tool emulation, and persistent upstream conversations
are intentionally excluded.

## Quick install

Requirements: Docker Engine, Docker Compose v2, and OpenSSL.

```bash
git clone https://github.com/ibrahimhalilkilicarslan/chat2api-web-gateway.git
cd chat2api-web-gateway
./scripts/install.sh --origin https://gateway.example.com
```

The installer:

1. generates independent cryptographic secrets,
2. writes a private `.env` with mode `0600`,
3. validates the Compose configuration,
4. builds the hardened image,
5. starts the gateway and waits for readiness.

It never prints the generated admin token. Retrieve it locally only when needed:

```bash
./scripts/show-admin-token.sh
```

Open `https://gateway.example.com/admin/`, sign in, add a dedicated DeepSeek web
session, run the credential health check, and create a client API key.

For configuration-only setup:

```bash
./scripts/install.sh --origin https://gateway.example.com --no-start
```

See the complete [Installation Guide](docs/installation.md).

## Developer setup

Requirements: Node.js `22.22.2+`, Corepack, and pnpm `11.18.0`.

```bash
corepack enable
corepack prepare pnpm@11.18.0 --activate
pnpm install --frozen-lockfile
pnpm setup -- --origin http://localhost:8080
pnpm doctor
docker compose -f compose.yaml -f compose.local.yaml up -d --build
```

The setup command refuses to overwrite an existing `.env` unless `--force` is
explicitly supplied. Forced replacement creates a timestamped private backup.
Developers can also retrieve the local token with `pnpm admin:token`.

## Client configuration

Use an API key created in the admin console:

```bash
export OPENAI_BASE_URL="https://gateway.example.com/v1"
export OPENAI_API_KEY="<client-api-key>"

curl "${OPENAI_BASE_URL}/models" \
  -H "Authorization: Bearer ${OPENAI_API_KEY}"
```

Example chat request:

```bash
curl "${OPENAI_BASE_URL}/chat/completions" \
  -H "Authorization: Bearer ${OPENAI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-v4-flash",
    "messages": [{"role": "user", "content": "Reply with exactly OK."}],
    "stream": false
  }'
```

## Supported contract

| Route | Support |
| --- | --- |
| `GET /health`, `/health/live`, `/health/ready` | Minimal health data |
| `GET /v1/models` | Models available through active DeepSeek web accounts |
| `POST /v1/chat/completions` | Text messages, JSON response, or SSE stream |
| `/admin/` | Account, client-key, health, activity, audit, and security controls |

Accepted chat fields are `model`, `messages`, `stream`, `web_search`, and
`reasoning_effort`. Messages contain `system`, `user`, or `assistant` roles and
string content. Images, files, tools, JSON mode, sampling controls,
`/v1/completions`, and `/v1/responses` fail explicitly.

Every request creates a fresh upstream conversation and deletes it when the
response finishes, fails, times out, or the client disconnects. Public response
IDs are generated by the gateway and never expose upstream session identifiers.

## Security model

- Bearer-only, fail-closed client authentication
- AES-256-GCM provider credential storage
- SHA-256 client-key storage; raw keys appear once
- Signed HttpOnly admin sessions, exact-origin checks, and CSRF protection
- No prompt, completion, cookie, provider payload, or credential persistence
- Fixed DeepSeek endpoints and strict text-only schemas
- Global/per-account concurrency, RPM, daily quotas, and circuit breakers
- First-byte, request, and stream-idle timeouts with abort propagation
- Non-root, read-only, capability-free production container

`CHAT2API_MASTER_KEY` must remain stable while encrypted provider credentials
exist. Losing it makes stored provider credentials unrecoverable. Back up the
runtime environment and SQLite volume separately and securely.

## Verification

```bash
pnpm check
docker compose -f compose.yaml -f compose.local.yaml config
docker build --tag chat2api-web-gateway:local .
pnpm smoke:container
```

A live provider smoke requires a dedicated test account and explicit operator
action:

```bash
CHAT2API_BASE_URL="https://gateway.example.com" \
CHAT2API_API_KEY="<client-api-key>" \
CHAT2API_SMOKE_MODEL="deepseek-v4-flash" \
CHAT2API_SMOKE_STREAM=true \
pnpm smoke:remote
```
