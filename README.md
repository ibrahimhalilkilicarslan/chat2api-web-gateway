# Chat2API DeepSeek Web Gateway

Security-hardened, web-only derivative of
[xiaoY233/Chat2API](https://github.com/xiaoY233/Chat2API). It exposes a small
OpenAI-compatible text-chat API backed only by a DeepSeek web session. Electron,
browser automation, official API fallback, arbitrary providers, tool emulation,
remote media, and persistent upstream conversations are intentionally absent.

## Supported contract

| Route | Support |
| --- | --- |
| `GET /health`, `/health/live`, `/health/ready` | Minimal health data |
| `GET /v1/models` | Models available through active DeepSeek web accounts |
| `POST /v1/chat/completions` | Text messages, JSON response or SSE stream |
| `/admin/` | Account, client-key, health, activity, and security controls |

Accepted chat fields are `model`, `messages`, `stream`, `web_search`, and
`reasoning_effort`. Messages contain `system`, `user`, or `assistant` roles and
string content. Images, files, tools, JSON mode, sampling controls,
`/v1/completions`, and `/v1/responses` fail explicitly instead of being silently
ignored.

Every request creates a fresh upstream DeepSeek conversation and deletes it when
the response finishes, fails, times out, or the client disconnects. Public
response IDs are generated by this gateway and never contain upstream session
identifiers.

## Security model

- Bearer-only, fail-closed client authentication
- AES-256-GCM provider credential storage
- SHA-256 client-key storage; raw keys appear once
- Signed HttpOnly admin sessions, exact-origin checks, and CSRF protection
- No prompt, completion, provider payload, cookie, or credential persistence
- Fixed DeepSeek endpoints and strict text-only schemas
- Global/per-account concurrency, RPM, daily quotas, and bounded circuit breakers
- First-byte, request, and stream-idle timeouts with abort propagation
- Non-root, read-only, capability-free production container

DeepSeek web endpoints are undocumented and may change or trigger account
controls. Use a dedicated account, review provider terms, and do not treat this
gateway as equivalent to an official API. Multiple accounts are for legitimate
capacity isolation and availability, not quota or access-control evasion.

## Development

Requirements: Node.js `22.22.2+`, Corepack, and pnpm `11.18.0`.

```bash
corepack enable
corepack prepare pnpm@11.18.0 --activate
pnpm install --frozen-lockfile
cp .env.example .env
pnpm dev
```

Generate every secret independently. Never commit `.env`.

```bash
openssl rand -base64 32
openssl rand -base64 48
```

`CHAT2API_MASTER_KEY` must remain stable while encrypted provider credentials
exist. `CHAT2API_BOOTSTRAP_API_KEY` is environment-managed and rotates on restart
without deleting admin-created client keys.

## Verification

```bash
pnpm check
docker compose -f compose.yaml -f compose.local.yaml config
docker build --tag chat2api-web-gateway:local .
pnpm smoke:container
pnpm smoke:remote
pnpm backup:sqlite -- --database /path/source.sqlite --output /secure/backup.sqlite
pnpm backup:verify -- --backup /secure/backup.sqlite
```

The container smoke uses disposable secrets and never calls DeepSeek. A provider
smoke requires a dedicated test account and explicit operator action.
